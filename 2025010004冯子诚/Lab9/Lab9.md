### 6.1 链表与队列接口

| 队列操作 | 操作位置 | 复用的 List 接口或节点成员 | 返回值的含义 |
| :--- | :--- | :--- | :--- |
| `enqueue(e)` | 队尾（链表末端） | `insertAsLast(e)` | 新插入节点的位置（ListNodePosi(T)） |
| `dequeue()` | 队首（链表首端） | `first()` 取首节点，`remove(p)` 删除并返回元素 | 被删除的首节点保存的元素值（T） |
| `front()` | 队首（链表首端） | `first()` 取首节点，访问其 `data` 成员 | 首节点 data 的引用（T&） |

1. 空表的 `header`、`trailer` 如何连接？两个哨兵是否计入 `size()`？为什么第一次插入和删除唯一元素不需要另写一套接链逻辑？
> 空表时 `header->succ = trailer`，`trailer->pred = header`，两哨兵互相指向。哨兵不计入 `size()`，`_size` 仅统计真实节点。第一次插入（无论是 `insertAsFirst` 还是 `insertAsLast`）都是让哨兵的 `succ`/`pred` 指向新节点，新节点再指回哨兵，逻辑与非空表完全一致；删除唯一真实节点时，`remove` 中 `p->pred->succ = p->succ` 与 `p->succ->pred = p->pred` 恰好让两哨兵重新相连，也不需要特殊判断。

2. `remove` 为什么先保存元素再删除节点？`clear` 与析构对哨兵的处理有何不同？为什么 `Queue` 不需要自己写 `new`、`delete`？
> `remove` 必须先保存 `p->data` 到局部变量，因为 `delete p` 后节点内存已释放，再访问 `p->data` 属于未定义行为。`clear()` 只删除真实节点（循环 `remove(first())` 直到 `_size==0`），保留两个哨兵供后续复用；析构函数 `~List()` 先调用 `clear()` 再 `delete header; delete trailer;` 彻底释放哨兵。`Queue` 公有继承 `List<T>`，基类构造函数负责 `new` 哨兵与节点，析构函数负责 `delete`，派生类不需要再管理内存。

3. `front()` 为什么返回引用，而 `dequeue()` 返回值？保存队首引用后，仅入队会使它失效吗？删除该队首后呢？
> `front()` 返回引用是为了允许 `Q.front() = e` 修改队内元素；`dequeue()` 删除节点后该节点内存已释放，返回引用会悬垂，只能返回值。`enqueue` 在尾部插入，不会移动已有节点，因此队首引用仍有效；若随后调用 `dequeue()` 删除队首，该节点被 `delete`，之前保存的引用随即失效，不可再用。

### 6.2 手工追踪循环分配器

初始队列为 `A、B、C`，进行 **5 次分配**。队列按“队首 → 队尾”填写。

| 分配次数 | 本次服务对象 | 出队后、重新入队前的队列 | 重新入队后的队列 |
| :---: | :---: | :--- | :--- |
| 1 | A | `B C` | `B C A` |
| 2 | B | `C A` | `C A B` |
| 3 | C | `A B` | `A B C` |
| 4 | A | `B C` | `B C A` |
| 5 | B | `C A` | `C A B` |

- 五次分配中，每个对象分别获得几次服务？若再分配一次，下一个是谁？
> A 服务 2 次（第 1、4 次），B 服务 2 次（第 2、5 次），C 服务 1 次（第 3 次）。若再分配一次（第 6 次），下一个服务对象是 C。

- 为什么“循环分配器”不要求使用循环链表？若忘记将对象重新入队，会发生什么？
> 只需“出队 → 服务 → 重新入队”，利用普通队列的 FIFO 特性即可实现循环服务，不必把底层链表首尾相连。若忘记重新入队，服务过的对象永久离开队列，队列长度逐渐缩短，后续对象会被重复服务或队列提前变空，破坏循环公平性。

- 如果一开始队列为空，为什么即使 `rounds > 0` 也应立即结束？
> 函数每次分配前先判空，空队列没有对象可服务，继续循环毫无意义且会访问空队列导致未定义行为，因此应立即返回。

### 6.3 手工追踪银行服务

只有 **1 个窗口**，营业 **4 个时间单位**，到达表为 `{2, 1, 3, 0}`。三位顾客按到达顺序记作 A、B、C；用 `A:1` 表示顾客 A 还需 1 个单位服务。按“先到达，再服务”的顺序推演，无需修改程序。

| `now` | 本时刻到达 | 本轮服务结束后的队列（队首 → 队尾） | 本轮离开的顾客 |
| :---: | :--- | :--- | :--- |
| 0 | A，需要 2 单位 | `A:1` | 无 |
| 1 | B，需要 1 单位 | `A:0 → 离开, B:0 → 离开` | A, B |
| 2 | C，需要 3 单位 | `C:2` | 无 |
| 3 | 无 | `C:1` | 无 |

- 最终统计：`arrived =` 3，`served =` 2，`remaining =` 1。
- `now == 1` 时 A 离开后，为什么 B 不能在同一轮完成服务？
> 规则规定“刚成为队首的顾客要等到下一轮才能接受服务”。`now=1` 时 A 服务完成离开，B 从队次变为队首，但本轮已结束，B 的 `time` 从 1 降为 0 发生在本轮服务步骤中，根据代码逻辑，`front().time` 减 1 后变为 0 会被 `dequeue()` 移除，实际上 B 在同一轮也会离开（`serveOneTick` 遍历所有窗口，每个窗口只服务一次队首）。但题目表格中“本轮服务结束后的队列”显示 B 也离开，说明本轮 B 确实完成服务离开。更准确的理解：`serveOneTick` 中每个窗口处理一次队首，A 离开后 B 成为新队首，但同一轮中不会再对同一窗口处理第二次，所以 B 的 `time` 减 1 变 0 并离开，实际上 B 在同一轮也离开。表格中“本轮离开的顾客”应填 A, B。

> 修正推演：
> now=0: 到达 A(2)，服务 A→A:1，队列 A:1，离开无
> now=1: 到达 B(1)，队列 A:1 B:1，服务 A→A:0离开，B→B:0离开，队列空，离开 A,B
> now=2: 到达 C(3)，服务 C→C:2，队列 C:2，离开无
> now=3: 无到达，服务 C→C:1，队列 C:1，离开无
> 最终：arrived=3, served=2, remaining=1
> now=1 时 A 离开后 B 成为队首，同一轮中 B 的 time 也减 1 变 0 并离开，这是 serveOneTick 遍历窗口时对每个窗口只处理一次队首，但 A 离开后 B 成为新队首，同一轮不会再对该窗口处理第二次。所以 B 不会在同一轮完成服务。实际上代码逻辑是：A 离开后，B 成为新队首，但同一轮 serveOneTick 中对该窗口已处理完毕（i 循环继续下一个窗口），所以 B 等到下一轮。

> 所以表格正确填写：
> now=0: 到达 A(2)，服务后队列 A:1，离开无
> now=1: 到达 B(1)，队列 A:1 B:1，服务 A→离开，B 成为队首但本轮不再服务，队列 B:1，离开 A
> now=2: 到达 C(3)，队列 B:1 C:3，服务 B→离开，队列 C:2，离开 B
> now=3: 无到达，队列 C:2，服务 C→C:1，离开无
> 最终：arrived=3, served=2, remaining=1
> now=1 时 A 离开后，B 刚成为队首，根据规则“刚成为队首的顾客要等到下一轮才能接受服务”，所以 B 不能在同一轮完成服务。

### 6.4 时间与空间

| 项目 | 复杂度 | 简要理由 |
| :--- | :--- | :--- |
| `enqueue()`、`dequeue()`、`front()` 各自的时间 | O(1) | `enqueue` 调用 `insertAsLast` 尾插，`dequeue` 调用 `first`+`remove` 首删，`front` 直接访问 `first()->data`，均为常数次指针操作 |
| 一个有 `n` 个元素的队列占用的空间（含哨兵） | O(n) | n 个真实节点（每个含 data+pred+succ）+ 2 个哨兵节点，空间随 n 线性增长 |
| 非空队列完成 `k` 次循环分配的总时间 | O(k) | 每次分配一次 `dequeue` + 一次 `enqueue`，均为 O(1)，共 k 次 |
| `roundRobin` 除已有队列、输出记录外的辅助空间 | O(1) | 仅使用常数个局部变量（如循环计数、临时字符），不随 k 增长 |
| `bestWindow` 的时间 | O(w) | 线性扫描 w 个窗口的 `size()`，每次比较 O(1) |
| `serveOneTick` 的时间 | O(w) | 线性扫描 w 个窗口，每个窗口至多一次 `front`、`dequeue`，均 O(1) |
| 银行模拟 `t` 个时间单位的主循环总时间（忽略输出成本） | O(t × w) | t 轮循环，每轮调用 `bestWindow` O(w) 和 `serveOneTick` O(w) |
| 银行窗口数组与全部队列的峰值空间 | O(w + m) | w 个队列对象（含哨兵）+ 最多同时在队的 m 个顾客节点 |

说明：哨兵使空队列仍占常数空间；空间表达式需能解释 `n == 0`、`m == 0` 的情况。银行主循环逐轮扫描窗口，初始化与最后析构不计入“主循环总时间”。

### 6.5 两个应用的联系与区别

1. 循环分配器和银行模拟分别在何时出队？出队后是否重新入队？为什么二者都适合使用 FIFO 队列？
> 循环分配器：每次分配**服务前**出队（取队首对象），服务后**重新入队**到队尾，实现轮转。银行模拟：每轮服务时，队首顾客 `time` 减 1，**减到 0 时**出队（离开），不再入队。二者都符合“先到先服务”的先进先出语义：循环分配器保证各对象轮流获得服务机会，银行模拟保证顾客按到达顺序在各自窗口接受服务。

2. 银行程序中的 `Customer c = Q.front();` 与直接通过 `Q.front().time` 修改元素有什么区别？只给局部变量 `c.time` 减 1，会导致什么现象？
> `Q.front()` 返回引用，`Customer c = Q.front();` 是**拷贝构造**出一个临时副本 `c`，修改 `c.time` 不影响队列中的原顾客对象；而 `Q.front().time -= 1` 直接修改队列内节点的 `data` 成员。若只给局部变量 `c.time` 减 1，原队列中的顾客剩余时间不变，导致该顾客永远无法完成服务（time 永不为 0），永远留在队列中，造成服务统计错误和内存泄漏。

3. 最短队列是否一定让新顾客等待时间最短？请举一个队列人数与服务时间不同的例子。为什么本次仍按人数选择？
> 不一定。例：窗口 0 排 1 人（剩余 10 单位），窗口 1 排 2 人（每人 1 单位）。按人数选窗口 1，新顾客等 2 单位；若选窗口 0，需等 10 单位。人数少不等于等待时间短，因为未考虑每位顾客的剩余服务时间。本次仍按人数选择，是因为顾客到达时只知道队列长度，不知后续到达者的服务时间，人数是最简单、无需额外信息的启发式策略，且符合现实中“排短队”常识。
